# Writing

시럽에서 사용하는 문장을 일관되게 작성하는 방법이에요. 버튼, 검색 안내, 리워드, 결과 메시지에 사용된 표현을 바탕으로 정리했어요.

> SEED Writing의 항목 구성을 참고하되, 아래 예시와 적용 기준은 시럽의 기존 MD·Figma 문구를 기준으로 작성했어요. 이 페이지를 추가하면서 기존 앱 문구를 일괄 변경하지는 않아요. 새로 제안한 문장은 **작성 예시**로 구분해요. 금액·횟수·시간은 실제 운영 조건을 확인한 뒤 사용해요.

## 1. 익숙한 단어로 안내해요

사용자가 바로 이해할 수 있는 말로 현재 상황과 필요한 행동을 알려줘요. 내부 상태명과 개발 용어는 화면에 그대로 노출하지 않아요.

| 시럽에서 사용하는 표현 | 적용 기준 |
| --- | --- |
| `다시 시도하기` | 재시도가 가능한 결과 화면에서는 실행할 행동을 버튼으로 알려줘요. |
| `금 받는 상품을 검색해보세요` | 시스템의 검색 상태보다 사용자가 찾을 대상을 안내해요. |

**작성 예시**: ‘불러오기에 실패했어요. 잠시 후 다시 시도해 주세요.’처럼 상황과 해결 방법을 함께 적어요. 실제로 다시 시도할 수 없는 오류에 같은 버튼을 붙이지 않아요.

관련 문서: [Result](/components/result), [Search Field](/components/search-field)

## 2. 편안한 해요체를 사용해요

일반적인 안내는 ‘~해요’, ‘~할 수 있어요’처럼 자연스럽게 작성해요. 불필요한 높임말을 반복하지 않아요. 버튼·메뉴는 짧은 동작형으로 작성해도 괜찮아요.

| 기존 시럽 문구 | 문장의 역할 |
| --- | --- |
| `3금을 받았어요!` | 리워드 수령 결과를 알려요. |
| `광고가 나와요` | 행동 전에 알아야 할 조건을 안내해요. |
| `알려드려요!` | 안내 영역의 제목으로 사용해요. |

법적 고지나 별도로 승인된 안내 문구는 해당 기준을 유지해요. 기존 `3초 후 금 받는 광고가 재생됩니다`를 말투 통일만을 이유로 임의 변경하지 않아요.

관련 문서: [Result](/components/result), [Bubble](/components/bubble), [Bottom Info](/components/bottom-info)

## 3. 숫자와 리워드 단위를 함께 보여줘요

금액·수량·횟수·시간은 숫자로 표시하고 의미를 알 수 있는 단위를 함께 적어요. 금과 원, 스탬프를 같은 단위처럼 사용하지 않아요.

| 기존 시럽 문구 | 확인할 내용 |
| --- | --- |
| `매일 3금` | 지급 주기와 리워드 수량이 실제 조건과 맞는지 확인해요. |
| `상품 찜하고 매일 3금 받으세요` | 필요한 행동과 받을 수 있는 금액을 함께 안내해요. |
| `3초 후 금 받는 광고가 재생됩니다` | 시간의 단위와 이후 동작을 명확히 알려요. |

본문·버튼·배지에 같은 리워드를 안내하면 금액을 일치시켜요. 예제의 3금·3초를 모든 서비스의 고정 정책으로 확장하지 않아요. 정확한 수량을 모르는 상태에서 임의의 금액을 넣지 않아요.

관련 문서: [Badge](/components/badge), [Button](/components/button), [Result](/components/result)

## 4. 서비스 용어를 일관되게 사용해요

디자인 시스템 문서에서는 보상 유형을 설명할 때 ‘리워드’를 사용할 수 있어요. 실제 앱에서는 기존 화면처럼 ‘금’, ‘스탬프’ 등 받는 대상을 구체적으로 표현해요.

| 용어 | 사용 기준 |
| --- | --- |
| 금 | 리워드 수량과 받을 수 있는 대상을 안내할 때 사용해요. |
| 스탬프 | 쿠팡의 스탬프 리워드 안내와 배지에 사용해요. |
| 찜하기 | 쇼핑 검색 후 참여하는 미션을 설명할 때 사용해요. |
| 골드톡 | 실제 서비스 이름을 가리킬 때 유지해요. |

`Gold`, `Stamp`, `Placeholder`, `Checked` 같은 속성명은 디자인·개발 문서에서 정확하게 사용해요. 사용자에게 보여주는 안내 문장에는 내부 속성명을 그대로 사용하지 않아요.

관련 문서: [Badge](/components/badge), [Search Field](/components/search-field), [Bubble](/components/bubble)

## 5. 버튼에는 실행할 행동을 적어요

누른 뒤 무엇이 일어나는지 예상할 수 있는 문구를 사용해요. 기능 이름이나 추상적인 상태보다 사용자가 실행할 동작을 먼저 알려줘요.

| 기존 시럽 문구 | 표현하는 행동 |
| --- | --- |
| `할 일 추가하기` | 목록에 할 일을 추가해요. |
| `혜택 받기` | 해당 혜택을 받아요. |
| `10금 받기` | 받을 수 있는 금의 수량을 명시해요. |
| `참여 방법 보기` | 참여 방법을 설명하는 내용으로 이동해요. |

단순히 안내를 읽고 닫는 경우에는 ‘확인’을 사용할 수 있어요. 두 버튼을 제공할 때는 각각 실행할 행동이 구분되게 작성해요. 이동인지, 추가로 불러오는 동작인지도 문구와 화살표 방향이 서로 맞아야 해요.

관련 문서: [Button](/components/button), [Text Button](/components/text-button), [List Footer](/components/list-footer), [Dialog](/components/dialog)

## 6. 할 수 있는 행동을 중심으로 안내해요

조건을 설명할 때는 가능한 행동을 먼저 알려줘요. 다만 오류·종료·이용 불가 상태를 긍정적인 표현으로 감추지는 않아요.

`상품 찜하고 매일 3금 받으세요`처럼 필요한 행동과 기대할 수 있는 결과를 연결해요. 참여 조건을 알리지 않은 채 금을 받을 수 있다고 단정하지 않아요.

작성할 때는 ‘무엇을 할 수 있는지 → 필요한 조건 → 다음 행동’ 순서로 읽히는지 확인해요. 지급이 지연되는 경우에는 완료된 것처럼 쓰지 않고 실제 상태와 가능한 다음 행동을 안내해요.

관련 문서: [Search Field](/components/search-field), [Result](/components/result), [Swipe](/components/swipe)

## 7. 사용자의 관점에서 결과를 알려줘요

내부 데이터의 변화보다 사용자가 무엇을 했고 어떤 결과를 얻었는지 표현해요.

| 표현 | 기준 |
| --- | --- |
| 기존 `3금을 받았어요!` | 수령 결과를 직접 알려요. |
| 기존 `할 일 추가하기` | 사용자의 행동을 나타내요. |
| 작성 예시 `할 일을 추가했어요.` | 행동이 실제로 끝난 뒤에만 사용해요. |

‘처리되었습니다’, ‘등록 처리가 완료되었습니다’ 같은 내부 처리 중심 표현을 반복하지 않아요. 다만 오류 원인이나 법적 의미를 정확히 전달해야 한다면 짧게 줄이는 것보다 의미를 우선해요.

관련 문서: [Result](/components/result), [Button](/components/button), [Toast](/components/toast)

## 8. 진행·받기 가능·수령 완료를 구분해요

조건을 충족한 상태와 실제 리워드를 받은 상태는 달라요. 문구뿐 아니라 버튼, 배지, 체크 표시도 같은 상태를 나타내야 해요.

| 상태 | 시럽에서 확인한 기준 |
| --- | --- |
| 참여 전·진행 중 | 필요한 행동이나 진행 상황을 안내해요. 아직 금을 받았다고 표현하지 않아요. |
| 받기 가능 | `10금 받기`처럼 실행할 동작과 받을 수 있는 수량을 안내해요. |
| 수령 완료 | `받기 완료`, `3금을 받았어요!`처럼 실제 지급 결과를 표시해요. |
| 미션 완료·금 수령 후 | Search Field를 `금 받는 상품을 검색해보세요`로 변경하고 Dot을 숨겨요. |

검색창에서 입력이 시작되어 Dot이 안 보이는 것만으로 미션 완료라고 판단하지 않아요. ‘3금을 받았어요!’의 금액도 실제 지급 결과와 맞춰요.

관련 문서: [Button](/components/button), [Badge](/components/badge), [Bubble](/components/bubble), [Search Field](/components/search-field)

## 9. 사용자의 상황을 배려해요

내역이 없거나 로딩에 실패한 상황에서 사용자의 잘못을 단정하지 않아요. 필요한 설명과 가능한 다음 행동을 제공해요.

Result는 검색 결과 없음, 내역 없음, 오류, 재시도, 이용 불가, 모두 확인한 상태, 리워드 수령 결과를 구분해요. 화면이 비어 보인다고 모두 같은 안내를 사용하지 않아요.

‘오늘의 콘텐츠를 모두 확인했어요’는 아직 내역이 없는 상태와 달라요. 다음 콘텐츠를 확인할 시점을 함께 안내해요. 축하 표현은 실제 성취나 리워드 수령과 연결하고 모든 안내에 반복하지 않아요.

관련 문서: [Result](/components/result), [Dialog](/components/dialog)

## 10. 한 문장에는 하나의 내용을 담아요

제목은 핵심을, 본문은 필요한 조건과 설명을, 버튼은 행동을 맡아요. 같은 말을 모든 영역에 반복하지 않아요.

Bubble의 `광고가 나와요`는 실행 전 조건을 짧게 보충해요. 자세한 유의 사항을 작은 버블이나 버튼 안에 몰아넣지 않아요. Bottom Info에는 관련 내용을 묶어 제공하고, Dialog에는 결정에 필요한 내용을 우선 배치해요.

글자 수 제한이 있는 입력 영역은 해당 컴포넌트의 최대 글자 수 기준을 따라요. 문장이 길어진다는 이유만으로 마스터 높이·글자 크기를 임의로 바꾸지 않아요.

관련 문서: [Bubble](/components/bubble), [Bottom Info](/components/bottom-info), [Dialog](/components/dialog), [Text Field](/components/text-field)

## 11. 시럽의 일상적인 행동과 혜택을 연결해요

SEED의 지역 맥락 항목은 시럽에 맞게 ‘일상 행동과 리워드’로 바꿔 적용해요. 시럽에서는 찜하기·페이지 방문·뉴스 읽기·쇼핑처럼 사용자가 실제로 하는 행동이 혜택과 어떻게 연결되는지 알려줘요.

| 기존 시럽 문구 | 전달하는 내용 |
| --- | --- |
| `페이지 방문하고 금 받기!` | 페이지 방문과 받을 수 있는 금을 연결해요. |
| `누르고 골드톡 알림 받기!` | 누른 뒤 실행되는 기능을 안내해요. |
| `상품 찜하고 매일 3금 받으세요` | 미션 행동과 리워드 조건을 함께 전달해요. |

광고 시청·참여 조건·차감처럼 실행 전에 알아야 할 내용은 빠뜨리지 않아요. ‘무조건’, ‘반드시’, ‘바로 지급’ 같은 확정 표현은 확인된 운영 조건이 있을 때만 사용해요.

관련 문서: [Toast](/components/toast), [Bubble](/components/bubble), [Search Field](/components/search-field)

## 12. 느낌표는 필요한 순간에 사용해요

리워드 수령이나 짧은 행동 안내에는 기존 문구처럼 느낌표를 사용할 수 있어요. 모든 문장에 붙이거나 연속해서 사용하지 않아요.

`3금을 받았어요!`, `알려드려요!`, `페이지 방문하고 금 받기!`는 현재 화면에서 쓰이는 예시예요. 오류·제한·이용 불가 안내에는 같은 분위기를 기계적으로 적용하지 않아요.

관련 문서: [Result](/components/result), [Bottom Info](/components/bottom-info), [Toast](/components/toast)

## 13. 띄어쓰기와 이름 표기를 구분해요

일반 문장은 읽기 자연스럽게 띄어 쓰고, 서비스명·확정된 UI 라벨은 원본 표기를 확인해요. 이름과 일반 문장을 같은 방식으로 기계적으로 붙이거나 나누지 않아요.

| 기존 표기 | 적용 범위 |
| --- | --- |
| `할 일 추가하기` | 기존 버튼 라벨을 그대로 참조해요. |
| `알림받기` / `알림받는 중` | Button / Alert에 쓰인 기존 라벨이에요. 문구를 바꿀 때는 해당 서비스와 원본 컴포넌트도 함께 확인해요. |
| `금 받는 상품을 검색해보세요` | 현재 Search Field 안내 문구예요. |

문서에서 발견한 과거 레이어명이나 속성명을 새 UI 문구의 표기 기준으로 삼지 않아요. 기존 표기를 개선할 경우에는 예제·마스터·MD가 서로 다르게 남지 않도록 함께 갱신해요.

관련 문서: [Button](/components/button), [Search Field](/components/search-field)

## 14. 문장과 짧은 라벨의 문장부호를 구분해요

설명 문장은 끝을 분명하게 맺고, 짧은 제목·버튼·메뉴·배지는 불필요한 마침표를 생략해요. 리워드나 금액만 적는 배지에 문장부호를 추가하지 않아요.

| 형태 | 예시 |
| --- | --- |
| 버튼 | `할 일 추가하기`, `혜택 받기`, `받기 완료` |
| 짧은 리워드 안내 | `매일 3금` |
| 결과 안내 | 기존 `3금을 받았어요!` |
| 설명 문장 | 작성 예시 `자세한 조건은 안내 내용을 확인해 주세요.` |

버튼이 여러 줄이 되거나 제목이 길어져도 문장부호만으로 문장의 역할을 바꾸지는 않아요. 해당 컴포넌트의 문구 길이와 줄 수 기준을 함께 확인해요.

## 15. 가까운 날짜는 오늘과의 관계로 보여줘요

알림·활동·적립 내역처럼 최근 기록을 살펴보는 화면에서는 오늘과의 관계를 먼저 보여줘요. 오늘 발생한 기록은 시간만, 어제 기록은 ‘어제’로 표시해요. 시간까지 구분해야 하는 화면에서는 ‘어제’ 뒤에 시간을 함께 적어요.

아래는 **시럽에서 정한 날짜·시간 표기 기준**이에요. 오늘·어제의 구분과 시간 표시 방식은 시럽의 사용 맥락에 맞춰 정했으며, 기존 화면의 날짜를 일괄 변경하지 않아요.

| 기록의 날짜 | 기본 표기 | 시간이 필요한 화면 | 적용 기준 |
| --- | --- | --- | --- |
| 오늘 | `14:30` | `14:30` | ‘오늘’을 반복하지 않고 시간만 보여줘요. |
| 어제 | `어제` | `어제 14:30` | 시각으로 기록을 구분해야 할 때만 시간을 붙여요. |
| 그 이전 · 올해 | `11월 21일` | `11월 21일 14:30` | ‘그제’, ‘3일 전’, ‘지난주’ 대신 실제 날짜로 보여줘요. |
| 그 이전 · 다른 해 | `2025년 12월 31일` | `2025년 12월 31일 14:30` | 연도를 생략해 올해 기록처럼 보이지 않게 해요. |

‘+시간’은 표기 조합을 뜻해요. 화면에 `어제 + 14:30`처럼 더하기 기호를 쓰지 않고, 공백 하나로 연결해 `어제 14:30`으로 표시해요. 시간은 기존 시럽의 `13:00` 표기와 맞춰 24시간제 `HH:mm`으로 통일해요. 한 자리 시·분도 `09:05`처럼 두 자리로 적으며, 같은 목록에서 `오후 2:30`과 `14:30`을 섞지 않아요.

시간이 순서나 식별에 필요한 채팅·상세 이력에서는 날짜와 시간을 함께 보여줘요. 읽지 않은 알림 등 날짜만으로 충분한 목록에서는 어제 이후의 시간은 생략해요. 화면마다 항목별로 임의 선택하지 않고 같은 목록에는 같은 표시 방식을 적용해요. 시간은 절대 시각으로 통일해요. 갱신 시각도 `14:30 기준` 또는 `어제 14:30 기준`으로 표시하고, `방금`, `5분 전`, `2시간 전` 같은 상대 시간은 사용하지 않아요.

### 날짜만 있거나 날짜로 묶은 화면

| 상황 | 표시 방법 |
| --- | --- |
| 원본에 날짜만 있고 시각이 없음 | 오늘은 `오늘`, 어제는 `어제`, 그 이전은 날짜로 표시해요. `00:00`을 임의로 만들지 않아요. |
| 날짜별 그룹 제목 | `오늘`, `어제`, `11월 21일`처럼 날짜를 표시해요. 오늘 그룹 제목을 시간으로 바꾸지 않아요. |
| 그룹 아래 기록 | 시각이 필요하면 `14:30`만 표시하고, 같은 날짜를 매번 반복하지 않아요. |

### ‘어제’는 24시간 전이 아니라 달력 날짜예요

한국 서비스의 기본 판단 시간대는 `Asia/Seoul`이에요. 현재 시각과 기록 시각을 같은 시간대로 바꾼 뒤 날짜를 비교해요. 기기 시간대와 서버 시간대를 섞어 오늘·어제가 달라지지 않게 해요. 해외 서비스는 해당 서비스가 정한 표시 시간대를 일관되게 사용하고, 사용자가 알아야 할 경우 시간대도 안내해요.

- 11월 23일 `00:05`에 보는 11월 22일 `23:55` 기록은 10분 전이어도 `어제` 또는 `어제 23:55`예요.
- 11월 23일 `23:55`에 보는 같은 날 `00:05` 기록은 `00:05`예요. 경과 시간이 길다는 이유로 ‘어제’로 바꾸지 않아요.
- 1월 1일에 보는 12월 31일 기록도 우선 ‘어제’로 판정해요. 정확한 연도가 필요한 상세 기록은 전체 날짜를 보여줘요.
- 화면을 자정 이후에도 열어두거나 다시 돌아오면 기준 날짜를 갱신해요. 오늘 시간 표기가 다음 날에도 그대로 남지 않게 해요.

### 정확한 날짜가 중요한 곳은 전체 날짜를 유지해요

이벤트 마감·예약·지급 예정일·유효기간·증빙·정산 상세·웹 문서의 업데이트 이력처럼 날짜 자체를 확인하거나 나중에 다시 인용하는 정보는 상대 날짜만으로 바꾸지 않아요. 예를 들어 `2026년 11월 23일 18:00까지`처럼 실제 일시를 명시해요. ‘오늘 마감’을 함께 쓰더라도 정확한 마감 일시를 확인할 수 있어야 해요.

미래 일정을 지난 기록용 표에 넣지 않아요. ‘내일’, 예정일, 마감까지 남은 시간은 별도의 일정 기준으로 다루며 임의로 ‘오늘’이나 ‘어제’로 보정하지 않아요. 날짜가 없거나 잘못된 값이면 숨기거나 ‘날짜 확인 중’ 등 실제 상태에 맞게 안내해요.

### 날짜 형식 참고와 시럽 자체 기준

- [당근 SEED · International Design](https://seed-design.io/foundations/international-design): 한국어의 연·월·일 순서와 날짜·시간 조합 형식만 참고했어요. 오늘·어제 전환이나 표시 범위의 근거로 사용하지 않아요.

오늘·어제의 판정, 24시간제 선택, 어제 이전의 날짜 표시, 예외 범위는 사용자 요청을 바탕으로 정리한 시럽 기준이에요. 실제 도입 전에 적용 화면과 시간 필요 여부를 확인해요.
